## 1. The click engine

The single biggest finding of the session. The original loop **could not exceed ~32 clicks per
second** regardless of the slider, and ran ~20% slow even at the default 10.

Cause: `Task.Delay` quantises to the ~15.6 ms system timer, so above roughly 60 CPS both halves of
each cycle rounded to `Delay(1)` and each actually took ~15.6 ms. The delay also never subtracted
time spent in `SendInput`, so error compounded.

Three changes fixed it:

1. `timeBeginPeriod(1)` for the life of the loop — takes the timer to ~1 ms.
2. **Absolute deadline accumulation** — each half-cycle advances a timestamp by exactly its share of
   the period, so overhead cannot compound. A resync guard drops the deadline forward if the loop
   falls >100 ms behind, so it never bursts to catch up.
3. Optional spin-wait for the last 2 ms, gated behind *Ultra Accuracy*.

Measured (this code, `SendInput` removed, 16-core machine):

| target CPS | rate (off) | jitter (off) | CPU (off) | rate (on) | jitter (on) | CPU (on) |
|---|---|---|---|---|---|---|
| 10 | 10.0 | 0.50 ms | ~0 | 10.0 | 0.00 ms | 0.03 core |
| 60 | 60.0 | 0.51 ms | ~0 | 60.0 | 0.05 ms | 0.13 core |
| 100 | 100.0 | 0.33 ms | ~0 | 100.0 | 0.04 ms | 0.28 core |
| 150 | 150.0 | 0.53 ms | 0.01 core | 150.0 | 0.02 ms | 0.26 core |

**This corrected an earlier claim of mine.** I had said Ultra Accuracy was needed to reach high
rates. It is not — the rate is exact either way. What spinning buys is *evenness between individual
clicks* (10–25× less jitter) for up to a third of a core. The UI label was rewritten accordingly.

Other engine work:

- Moved off the UI thread onto a dedicated `ClickEngine` thread. Spinning on the dispatcher would
  freeze rendering. UI controls have thread affinity, so the engine reads an immutable
  `ClickSettings` snapshot published through a `volatile` field.
- **CDC implemented for real.** It previously did nothing: press and release were sent in one
  `SendInput` call, so hold time was always zero. Now split, with a `finally` that releases the
  button if cancellation lands mid-click — otherwise stopping would leave the left button held
  across the whole desktop.
- `WaitUntil` slices its coarse sleep into 20 ms chunks. At 1 CPS a single hold runs to hundreds of
  milliseconds, and an uninterruptible sleep there kept the button down that long after a stop.
  Measured cancellation latency afterwards: **2–5 ms**.

## 2. Input and hotkeys

**Hotkeys are polled on a dedicated thread**, not driven by window events.

- Routed `KeyDown` only fires while this window has focus — precisely when a game does not.
- Mouse side buttons never route to the window at all.
- A `DispatcherTimer` ticks at `Background` priority, below rendering. Under load its interval
  stretches, and a press *and* release landing inside one gap cancel out — the edge is never seen.
  That was the reported "sometimes it doesn't stop".

A binding is now a `HotkeyBinding` — virtual-key code plus display name — so a keyboard key and a
mouse side button are the same kind of thing. Three bindings: start/stop (F6), Shaky Tracking (F7),
instant replay (F8). Left mouse is deliberately unbindable, being the button the app synthesises.

Rebinding is inline — the button becomes "Select A Hotkey" — and captures on `PreviewKeyDown`,
ahead of the focused control, because a `Button` treats Space and Enter as activation during
`KeyDown` and would re-trigger itself.

Fixed along the way: hold mode never releasing; auto-repeat thrashing the toggle; rebinding not
reaching the engine's hardcoded `VK_F6`; Escape unreachable behind the hotkey comparison.

## 3. Shaky Tracking

Was misread — and misimplemented — as click-*timing* jitter. It is **camera movement**, for
tracking practice.

Rebuilt as its own thread, independent of clicking, with four configurable direction magnitudes.

**Bounded offsets, not a random walk.** The reference script takes an independent random step each
tick, which accumulates. Simulated over 10 s at 30 Hz:

```
random walk    : final -79 px, max excursion 82 px
bounded offset : final  -2 px, max excursion  4 px
```

For aim training a crosshair that slides off screen is a fault, not a handicap.

### First-person gate — still unresolved

Only shakes while Roblox is in front and in first person. The obvious test — *is the cursor
hidden* — **does not work**: Roblox swaps the cursor bitmap (arrow ↔ crosshair) rather than hiding
it, so `CURSOR_SHOWING` stays set and the gate never opened. Found from video frames the user
supplied.

Current approach compares `CURSORINFO.hCursor` against `LoadCursor(NULL, IDC_ARROW)`. Verified the
mechanism (5 of 5 standard cursor handles distinct; live cursor correctly identified), but **not
verified against Roblox** — not installed on this machine. If Roblox draws its crosshair into the 3D
scene rather than as the cursor, this approach is dead and the fallback is a manual toggle.

## 4. New pages

| Page | Contents |
|---|---|
| **Presets** | Cards with CPS/CDC bar, full-profile save, edit, delete, restore defaults |
| **Tweaks** | Nine Windows settings, each recording prior state before writing |
| **Optimizations** | Temp cleaner, memory panel, Tracking Helper, QoS toggle |
| **Mod** | FPS Boost FastFlags from Roblox's published allowlist |
| **History** | All-time / this-session / by-day clicking totals |
| **Recorder** | Screen capture, instant replay, upload for a shareable link |

**Presets became full profiles** — mode, Ultra Accuracy, and all four shake values, not just two
numbers. Applying one sets up a whole session. Backward compatible: an old file loads with sensible
shake defaults rather than zeroes.

**Tweaks records prior state before writing**, so Revert restores what the machine actually had. A
null recorded value means "did not exist", so revert deletes rather than inventing a zero. There is
deliberately **no Apply All** — one click silently changing several system settings, two of them
registry writes, is how people end up unable to undo something.

Core parking is driven through the registry rather than `powercfg` aliases: Windows ships
`CPMINCORES` hidden (`Attributes = 1`), and while hidden `powercfg -q` prints nothing for it even
with explicit GUIDs. Query-based detection reports "unreadable" on a stock machine.

**Temp cleaner** scans `%TEMP%` and `%SystemRoot%\Temp` and nowhere else, skips anything touched in
the last 24 hours, and **refuses to cross a reparse point** — a junction inside temp can point
anywhere. Measured here: 181,189 files / 3,186 MB eligible, 1.5 s to walk, hence off the UI thread.

**Recorder** uses ffmpeg `gdigrab` behind a three-method seam so `Windows.Graphics.Capture` can
replace it later. Graceful stop matters more than it looks:

```
graceful stop :  855,736 bytes  ->  valid mp4
killed        :  786,480 bytes  ->  UNREADABLE: moov atom not found
```

**Instant replay** buffers MPEG-TS segments, not MP4 — an MP4 only becomes readable once its index
is written, so the segment being written *now* would be unusable, and that is the second before the
hotkey. Verified bounded and fast: 20 segments held at a 20 s capacity, save took **63 ms** by stream
copy.

## 5. Persistence

Five JSON files beside the executable, all gitignored as user state:

| File | Contents | Written |
|---|---|---|
| `hotkey_settings.json` | Three bindings as virtual-key + name | on rebind |
| `app_settings.json` | Rates, shake, toggles, mode, hide-values, replay, window placement | 1 Hz when dirty, and on close |
| `click_presets.json` | The whole preset list | on edit |
| `tweak_state.json` | Prior values for applied tweaks | on toggle |
| `history.json` | Lifetime and per-day totals | every 30 s, and on close |

Every loader degrades to defaults on missing or corrupt input; all verified with deliberately
corrupt files. `HotkeySettings` also reads the older "name of a WPF `Key`" format.

Window size uses `RestoreBounds`, not `Width`/`Height` — while maximised those report the maximised
size. Position is validated against the virtual screen before restoring, so a window remembered on
an unplugged monitor cannot open off-screen.

## 7. Where I pushed back

- **Fleasion** — no Roblox policy either way, general ToS points against, safety unverifiable. By
  the user's own stated standard, it does not clear the bar.
- **Font replacement** — same category as Fleasion (client asset modification), unlike FastFlags
  which Roblox explicitly allowlisted.
- **Medal / YouTube upload** — Medal's API only triggers its own installed client; YouTube locks
  uploads from unaudited API projects to private, with no appeal, so the link would not work.
- **Free RAM** — built as asked, labelled for what it does: trimming working sets makes a number
  rise and then fall again.
- **QoS** — built as asked. DSCP is a request; most consumer routers ignore it and it only matters
  under congestion. Badge reads "Depends entirely on your router".
- **`Windows.Graphics.Capture`** — switched to ffmpeg on "do whatever it takes", because I could
  actually verify ffmpeg's behaviour and could not have verified several hundred lines of D3D
  interop.

## 8. Incidental finding — worth more than any tweak in the app

The machine's **Ethernet is linked at 10 Mbps on a gigabit adapter**, with Speed & Duplex set to
Auto Negotiation:

```
adapter    : Realtek PCIe GbE Family Controller
link speed : 10 Mbps
latency    : min 11 ms  avg 15.8 ms  max 22 ms  jitter 11 ms
```

Auto-negotiation not being forced makes this diagnostic: it is a physical-layer problem, almost
always a bad or too-old cable (gigabit needs all four pairs) or a bad port. A 10 Mbps link saturates
from almost nothing, and queuing is what produces latency spikes. **Try a different cable** — this
affects gameplay more than anything on the Optimizations page.

## 11. How things were verified

No WPF UI was driven — the app injects mouse input, so automating it is a bad idea. Instead,
throwaway console harnesses compiled directly against the real source files, so every check ran the
shipping code rather than a copy of it:

- timing and cancellation latency against a synthetic source
- persistence round-trips for all five stores, including corrupt and legacy files
- the CPU calculation cross-checked against Windows' own performance counter (21.3% vs 23.5% over
  adjacent sample windows)
- tweak detection against real system state, read-only
- the temp scanner cross-checked against an independent PowerShell measurement (181,189 vs 181,174
  files — the gap is temp churn between runs)
- XAML resource ordering audited for forward references

Verification twice caught bugs that reasoning had missed: the `powercfg` core-parking query
returning nothing on a stock machine, and the cursor test that could never become true in Roblox.
